# Ranch State Distillation — the ranch, sampled into state.phext

Will's design (2026-11-06): track the ranch state across time as **distillation only**. The purpose is biofeedback — the Exocortex is part of how Will's brain models itself, and a steady, distilled state signal is what lets him learn to read and steer it. Scheduled embodiment: cron `state-phext-sampler` (every 5 minutes, America/Chicago), which runs `scripts/state_sampler.py` and stays silent unless a cycle fails.

## The pipeline (one cycle, fully deterministic — no LLM in the loop)

1. **Pull.** One `ranch fanout` pass through the ranch proxy (`~/workspace/ranch-proxy/ranch`, the only sanctioned route to the fleet) over every enabled node: load, core count, top processes, ollama / render / gateway markers, GPU edge temperature. CPU Tctl comes from the fanout footers, which the proxy measures itself — including for nodes it thermally skips, so the hotspot is never invisible at the moment it matters most. Disabled nodes (Aurora Continuum, Best Willow, Delta Wood) are recorded as down from `nodes.json`; an enabled node that refuses auth (Uncanny Valley — jared's key grant is outstanding) is recorded as no-access, never as down.
2. **Summarize.** A template composes one or two lines of plain language: nodes up out of 17, the busy set (render / inference / compute, by node) or "fleet idle", average Tctl across the nodes reporting, the hotspot (flagged when it crosses the 75 °C sustained cap), a GPU hotspot clause only at 65 °C or above, then the down and no-access lists. A node is busy when a render marker is live, when ollama is up under load (≥ 0.5), or when load reaches three quarters of its cores.
3. **Coordinate.** The summary's holographic coordinate is computed with the Singular skill's own machinery — `check_singular.WORD_RE` tokenization (letters only; digits carry no words) and `task_coordinate`'s atlas load and component-wise merge (round half up, never below 1) — imported, never reimplemented. The timestamp is NOT part of the merged text: a state that reads the same distills to the same coordinate whenever it recurs.
4. **Store (WAL by construction — Will's ruling 2026-11-09, stated 01:42 and corrected by him minutes later).** Keep a minimum coordinate — the **floor**, the highest coordinate already written in `state.phext` — and enforce that every new write lands **strictly above it**. Previously written scrolls are immutable, and that is what makes the WAL automatic: phext serializes scrolls in coordinate order, so a strictly-greater write appends its delimiter delta and text at the file's tail and touches no byte already written (verifiable: after any cycle, the old file is a byte-exact prefix of the new one). Coordinate assignment is **indirect**: the summary's holographic coordinate is the entry's logical address; when the floor displaces the write to a higher physical coordinate, the stored line is prefixed with the logical coordinate (`logical | YYYY-MM-DD HH:MM TZ | summary`), and readers resolve the logical view by folding the physical scrolls in write order (`read_state_scrolls()` in the sampler). An occupied logical coordinate gains a line; nothing is ever overwritten or dropped. Why not the original parse → modify → implode → atomic-replace: the Muse VM substrate denies whole-file temp+rename writes (Errno 1 on the temp write; appends pass) — a substrate failure logged in the qexo design notes (EVALUATIONS.md, 2026-11-09). (An earlier same-night implementation appended to a separate `state.wal` file; Will corrected the reading — the WAL is a property of the coordinate discipline inside state.phext itself, not a sidecar file. The sidecar's two entries were migrated in under the floor discipline and the file retired.)

## What never enters the phext

Raw pulls live outside, as working state: `~/workspace/state-sampler/hidden_files/last-pull.json` (latest pull, overwritten) and `pulls.jsonl` (size-capped log). They are debugging surface only. If a fact matters long-term it will arrive as a summary line or not at all — that restraint is the design: the phext stays small and reviewable for years.

## Reading state.phext

- The physical file holds scrolls in write order at monotonically increasing coordinates; the **logical** view folds them: a line with an indirect prefix belongs to the logical coordinate it names, any other line to the physical scroll holding it. The sampler's `read_state_scrolls()` performs the fold; a raw parse (`~/workspace/phext/parse_phext.py state.phext`) shows the physical layout, whose high-coordinate tail is the displaced recent entries.
- Home (1.1.1/1.1.1/1.1.1) documents the layout and entry format. In the logical view, every scroll is one distilled state with its occurrence lines; Home's own prose lines fold to Home, not to the state scrolls.
- Scrolls cluster by resemblance in logical space — a changed hotspot or busy set moves the logical coordinate slightly; a change of a degree or a count does not move it at all (numbers ride in the line text). The logical map is the map of the shapes the ranch takes over time.
- Verify any entry's logical placement by re-running the singular `task_coordinate.py` on its summary text — the coordinate must match the recorded logical address exactly.

## Failure discipline

- One dead node never stalls a cycle: the fanout is parallel and timeout-bounded, and unreachable nodes are summarized as down / no-access, not retried.
- A cycle that cannot append leaves the phext untouched and exits nonzero; the cron reports only failures, briefly, and never edits the phext by hand or improvises a repair.
- Growth is linear in lines (288 pulls/day): roughly 53 KB/day of line text plus small delimiter overhead per displaced scroll — about 1.6 MB at 30 days, 5 MB at 90. If that ever needs trimming, the levers are cadence and line length, chosen by Will — never silent pruning of the record.
