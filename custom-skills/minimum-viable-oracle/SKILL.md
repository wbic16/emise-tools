# Minimum Viable Oracle — Lean-proved epistemic fidelity for research.phext

## Origin

Make sure information is organized at that level of fidelity. When new information comes to light, you'll re-structure research.phext to be the Minimum Viable Oracle for what we know, so far."*

The four statuses are Will's own frame (2026-11-03): intelligence is holding **true, unknown, false, and fiction** all at once without breaking. This skill makes research.phext hold them that way — explicitly, per claim, with the model of the holding itself machine-checked. It is charter rule 14 of the R&D tracker, and it extends charter rule 8: restructuring passes are henceforth MVO passes.

## The four statuses

Every claim-bearing unit of research.phext (a scroll; a single claim inside a scroll when the MVO pass splits one) holds exactly one status — the model's stance toward the claim:

- **TRUE** — established. Either true by stipulation (a definition we set: foundations, defined words, our own metrics) or backed by a verification receipt we can point to: a kernel check, a reproduction, a measurement we ran, a source fact checked at ingestion.
- **FALSE** — refuted, and kept. A claim the model once carried (or a paper asserted) that a refutation receipt contradicts: a recorded contradiction, a failed reproduction, a counterexample. False claims are knowledge; they are never silently deleted, only retired with their receipt and a redirect.
- **UNKNOWN** — recorded but not settled. The default for attributed claims: a paper asserting X makes "paper P asserts X" a fact of record, but X itself is Unknown until a receipt settles it. Open questions, synthesis inferences, and calibrated estimates (the Oracle ledger) are Unknown.
- **FICTION** — deliberate constructions, held as constructions: worked examples with invented entities, hypothetical scenarios, narrative framing devices. Fiction is never presented as fact and never promoted directly to True.

## Basis codes — the assignment rules

A status is never bare. Every registry entry carries a **basis** (why it holds that status) and an **evidence pointer** (the receipt, source, or scroll that backs the basis). The basis constrains the status:

| basis | meaning | allowed status |
|---|---|---|
| STIPULATION | we define it so (foundations, defined words, our metrics) | True |
| VERIFIED | verification receipt exists (kernel check, reproduction, measurement, checked source fact) | True |
| REFUTED | refutation receipt exists (contradiction, failed check, counterexample) | False |
| ATTRIBUTED | a source asserts it; we have not settled it | Unknown |
| OPEN | an open question in the tracker | Unknown |
| SYNTHESIS | Emise's inference, labelled [synthesis] | Unknown |
| ESTIMATE | calibrated judgement (Oracle ledger, progress estimates) | Unknown |
| CONSTRUCTION | deliberately invented for exposition | Fiction |

An entry whose status violates its basis row is an accuracy defect by definition — this table is the core of what "accurate" means, and it is what the Lean model checks.

## The registry

The registry is the organized form of the fidelity: one entry per claim-bearing unit — coordinate, one-line claim, status, basis, evidence pointer. It lives three ways from one source:

1. **Builder data** in `~/workspace/research-tracker/` (kind-based defaults from the scroll's coordinate class + an explicit overrides table where judgement overrides the default — the overrides table is where human judgement lives, and it is reviewed at every MVO pass).
2. **Chapter 1 §4 of research.phext** (coordinates 1.4.x): the registry rendered for readers, grouped by status, regenerated by the builder like the rest of the phext.
3. **`Registry.lean`**, generated from the same data, consumed by the Lean proof (§ below).

Classification defaults by scroll kind: foundations and defined words → True/STIPULATION; bibliographic records → True/VERIFIED (checked against the source at ingestion); paper claims and concepts drawn from papers → Unknown/ATTRIBUTED; open questions → Unknown/OPEN; synthesis scrolls and the narrative → Unknown/SYNTHESIS; Oracle ledger → Unknown/ESTIMATE; worked examples with invented entities → Fiction/CONSTRUCTION. Anything we actually checked (study measurements, test runs, kernel results) is promoted by override to True/VERIFIED with the receipt as its evidence pointer; anything refuted is entered as False/REFUTED with its receipt.

## The Lean step

Artifacts: `~/workspace/research-tracker/epistemic/` (Lean project, built on aletheia-core — Lean 4.35.0 — ranch-first like the rest of MOAT's proving). The model:

- `Status` (True/False/Unknown/Fiction), `Basis` (the eight codes), `Entry` (id, status, basis, evidence present), `Registry` (a list of entries).
- `Allowed : Basis → Status → Prop` — the table above, as data.
- `Accurate (r : Registry)` — the conjunction: **total** (every unit id in the phext appears), **unique** (no id twice), **basis-conformant** (every entry's status is allowed for its basis), **receipt-backed** (True entries carry VERIFIED or STIPULATION basis; False entries carry REFUTED; Fiction entries carry CONSTRUCTION).
- `LegalTransition` — a status change is legal only along these edges and only with the receipt the edge names: Unknown→True (verification receipt arrives), Unknown→False (refutation receipt), True→False (refutation receipt; the claim is demoted, history kept), False→Unknown (receipt invalidated), Fiction→Unknown (a construction is taken up as a real proposal), Unknown→Fiction (a claim is reclassified as exposition). No edge enters True without a verification receipt; Fiction never goes directly to True; every transition is itself recorded as a registry event.
- **Theorems (proved, no `sorry`, axioms enumerated):** the empty registry is accurate; entering a new conformant entry preserves accuracy; every legal transition preserves accuracy; the MVO restructure operations (merge two entries for one claim, split an entry, retire-with-redirect) preserve accuracy. And the instance theorem: the generated `Registry.lean` data for the current research.phext satisfies `Accurate` — re-proved after every ingestion, transition, or restructure. If it does not prove, the change is not done.

**The honesty boundary, stated once and kept:** Lean proves the *model* — that every claim is classified exactly once, that no True lacks a receipt of the right kind, that statuses only ever moved along legal edges, and that restructuring cannot break any of that. Lean does not and cannot prove that a receipt-backed True is true in the world; that rests on the receipts themselves — kernel checks, reproductions, measurements — which follow MOAT's verify-quantified-results discipline. The proof makes the bookkeeping incorruptible; the evidence standard makes the bookkeeping worth trusting.

## The MVO restructure

When new information arrives (a paper, a study, a verification or refutation result, a correction from Will), the ingestion is not complete until:

1. The delta is written (existing charter rules) **and** every touched unit's status is re-examined: new receipts trigger legal transitions, recorded as events with their evidence pointers.
2. The registry is regenerated, §4 re-rendered, and the Lean instance theorem re-proved.
3. The phext is left as the **Minimum Viable Oracle** for what we know so far: the smallest *organization* that (a) classifies every claim at four-status fidelity, (b) keeps provenance for every claim, (c) keeps False claims visible as False rather than deleting them, (d) keeps Unknowns visible as Unknowns rather than letting attribution blur into belief, and (e) answers from canonical scrolls alone — the Research Oracle fixed point, approached by organizing (de-duplicating, linking instead of restating, splitting any unit whose claims no longer share one status), never by discarding.

**No pruning (Will, 2026-11-07):** the minimum in Minimum Viable Oracle is a minimum of structure, never of content. This system requires no information to be pruned: in our R&D eyes all knowledge has a purpose, because we might be wrong — a False can be re-examined, a Fiction can turn out to be a proposal, an Unknown can settle either way. Retirement is always relocation with a redirect; the claim, its history, and its receipts stay reachable. (Contrast modern math's brittleness: binary truth plus explosion means one contradiction trivializes the whole edifice and a broken foundation is discarded wholesale — there is no native state for "held, useful, possibly wrong." Here being wrong is a first-class, survivable state: a claim falls True→False and the registry gets *more* accurate, not invalid.)

Rule 8's triggers (every 5 papers / 40 concepts / revealed overlap) now run as MVO passes under this discipline; a receipt that changes a load-bearing claim's status triggers an MVO pass on its own, without waiting for a count trigger.

## Reporting

Each ingestion or pass reports, alongside the Novelty Index: the registry counts by status (how much of the model is True / False / Unknown / Fiction), the transitions the new information caused, and the Lean verification result (instance theorem proved, phext sha the registry was extracted from, axiom surface). Expect the honest picture to be mostly Unknown — attributed claims dominate a young tracker, and the counts saying so is the fidelity working, not failing.
